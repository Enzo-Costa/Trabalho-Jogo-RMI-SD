1. Como o Sistema Funciona (Arquitetura)

Para manter o código simples e fácil de manter, organizamos a solução em apenas 3 programas Java independentes na raiz do projeto, sem nenhuma biblioteca externa. Eles se comunicam seguindo exatamente o fluxo da Figura 1 da especificação:

+-----------------------------------------------------------------------------------+
|               1. SERVIDOR DE MATCH (RMI) — [Passo 1: Bind no Registry]            |
|                      VM 152.92.236.14 • RMIRegistry Porta 98NN                    |
|        [Passo 3: lock.wait() retém Jogador 1 até Jogador 2 entrar no Match]       |
+-----------------------------------------------------------------------------------+
   |         ^                                                         ^         |   
   |         | (Passo 2) getOponent(...)     (Passo 4) getOponent(...) |         |   
   |         | (aguarda oponente)            (completa o par)          |         |   
   v         |                                                         |         v   
 (Passo 6) Retorno RMI:                                 (Passo 6) Retorno RMI:       
 Oponente + inicia: true                                Oponente + inicia: false     
+--------------------------+    (Passo 7) Handshake    +--------------------------+
|       2. JOGADOR 1       | <=========================> |       2. JOGADOR 2       |
|    VM: 152.92.236.16     | (Passo 8) Troca de Jogadas |    VM: 152.92.236.17     |
|   (inicia: true - 'X')   |   Sockets P2P (TCP / UDP)   |   (inicia: false - 'O')  |
+--------------------------+                             +--------------------------+
             |                                                         |             
             | (Passo 5) Multicast UDP                  Multicast UDP  |             
             v                                                         v             
+-----------------------------------------------------------------------------------+
|                           3. GRUPO MULTICAST DE DISPLAYS                          |
|         [Passo 5: joinGroup() — Display 1 (Canal 1), Display 2, Display N]        |
|                               IP: 225.1.1.NN:88NN                                 |
+-----------------------------------------------------------------------------------+
Passo a passo da partida:
  1. Passo 1 (Inicialização do Servidor): O ServidorMatch sobe na máquina do servidor (152.92.236.14), inicia o registro RMI na porta 98NN e publica o serviço de pareamento.
  2. Passo 2 (Entrada do Jogador 1): O primeiro jogador chama getOponent(...) via RMI informando seu IP, porta e se deseja jogar por TCP ou UDP.
  3. Passo 3 (Espera Sincronizada): Como ainda não há adversário com o mesmo protocolo na fila, o servidor coloca essa chamada em espera através de um wait(60000).
  4. Passo 4 (Chegada do Jogador 2): O segundo jogador se conecta ao RMI solicitando uma partida com o mesmo protocolo, completando a dupla.
  5. Passo 5 (Entrada dos Displays): Enquanto isso, os espectadores que quiserem assistir à partida rodam o Display, que entra no grupo multicast 225.1.1.NN:88NN.
  6. Passo 6 (Liberação do RMI): O servidor acorda a thread do Jogador 1 (com notifyAll()) e devolve para os dois jogadores os dados do adversário e quem fará a primeira jogada (inicia: true/false).
  7. Passo 7 (Conexão Direta entre os Jogadores): Os jogadores conectam seus sockets diretamente (TCP ou UDP) para iniciar o jogo.
  8. Passo 8 (Partida em Turnos e Multicast): Os jogadores alternam o envio de jogadas em JSON via Socket. A cada lance realizado, quem jogou envia o tabuleiro atualizado para o grupo Multicast para os Displays exibirem aos espectadores.

2. Máquinas, Portas e Protocolos

Configuração de rede utilizada nos testes nas máquinas virtuais da UERJ. O valor de NN representa o número da conta atribuída ao aluno no laboratório (por exemplo, conta 14 utiliza NN = 14):

Componente Onde Roda (VM) Porta / Endereço Protocolo
Servidor de Matchmaking 152.92.236.14 Porta 9800 + NN (ex: 9814) Java RMI
Jogador 1 (Quem inicia) 152.92.236.16 Porta livre (ex: 5001) TCP ou UDP
Jogador 2 (Segundo a jogar) 152.92.236.17 Porta livre (ex: 5002) TCP ou UDP
Displays (Espectadores) Qualquer máquina IP 225.1.1.NN na Porta 8800 + NN (ex: 8814) UDP Multicast

3. Formato das Mensagens (JSON)

Para não depender de bibliotecas externas (como Gson ou Jackson), toda a montagem e leitura de JSON foi feita com tratamento simples de Strings em Java puro.

3.1. Pareamento no RMI

O que o jogador envia ao chamar getOponent(...) e o que o servidor devolve:

Entrada enviada ao RMI (jsonIn) Resposta devolvida pelo Servidor (jsonRet)
{"ip":"152.92.236.16","porta":5001,"protocolo":"tcp"} {"ip":"152.92.236.17","porta":5002,"inicia":true}

3.2. Troca de Jogadas e Transmissão no Multicast

A cada turno, os jogadores enviam um para o outro e para os displays exatamente esta estrutura de mensagem:

{
  "Numero": 0,
  "Jogada": 4,
  "Tabuleiro": [0, 0, 0, 0, 1, 0, 0, 0, 0],
  "Resultado": "jog"
}
Campo Tipo Valores Significado no Jogo
Numero Inteiro 0 a 8 Contador sequencial do turno. Garante que ninguém pule ou repita jogadas.
Jogada Inteiro 0 a 8 Posição escolhida no tabuleiro (de 0 a 8).
Tabuleiro Lista de 9 inteiros 0, 1 ou 2 Estado de cada casa: 0 = vazio, 1 = X (Jogador 1), 2 = O (Jogador 2).
Resultado Texto "jog", "vit", "der", "emp" Situação da partida: em andamento (jog), vitória (vit), derrota (der) ou empate (emp).

4. Tratamento de Falhas e Regras do Jogo

Pensando na estabilidade do jogo em rede e nos requisitos da disciplina, implementamos alguns cuidados práticos:

  • Timeouts para evitar travamentos: Adicionamos um timeout de 60 segundos no RMI (caso um jogador entre e nenhum adversário apareça) e também no Socket TCP/UDP com setSoTimeout(60000), evitando que o processo fique congelado se o outro jogador fechar o terminal ou cair no meio da partida.
  • Prevenção contra jogadas inválidas (Anti-Cheat): A cada lance recebido, o programa confere se a casa já não estava preenchida e se a numeração sequencial do turno está em ordem. Se houver qualquer inconsistência, a jogada não é aceita e o estado anterior é reenviado para manter a integridade da partida.
  • Multicast sem jogadas duplicadas: Para não poluir a tela dos espectadores, apenas o jogador que acabou de fazer a jogada publica o estado no grupo Multicast (225.1.1.NN:88NN). Quem apenas recebeu o lance atualiza seu tabuleiro localmente sem reenviar.
  • Suporte a TCP e UDP (Bônus): O sistema suporta tanto conexões orientadas a fluxo (TCP) quanto por datagramas (UDP). O servidor de pareamento gerencia filas separadas por protocolo para que jogadores de TCP joguem entre si e jogadores de UDP também, cumprindo o bônus proposto.

5. Como Compilar e Rodar

1. Compilação (direta com javac, sem precisar de Maven ou Gradle):

javac *.java

2. Como rodar nas máquinas virtuais da UERJ (usando a conta 14 como exemplo):

• Terminal 1 na VM 152.92.236.14 (Inicia o servidor de pareamento RMI): 

java ServidorMatch 14

• Terminal 2 em qualquer VM ou máquina local (Inicia o display espectador):

java Display 14

• Terminal 3 na VM 152.92.236.16 (Conecta o Jogador 1): 

java Jogador 14 5001 152.92.236.14 tcp

• Terminal 4 na VM 152.92.236.17 (Conecta o Jogador 2 e inicia a partida): 

java Jogador 14 5002 152.92.236.14 tcp

💡 Dica: Para testar a versão em UDP, substitua tcp por udp. Para jogar outros jogos, basta passar o tipo no final do comando: ppt (Pedra, Papel e Tesoura) ou par_impar (Par ou Ímpar). Exemplo: java Jogador 14 5001 152.92.236.14 tcp ppt.
